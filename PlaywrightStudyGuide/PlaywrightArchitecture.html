// 01 — Foundation

What Is Playwright, and Why Should QA Engineers Care?

Playwright is an open-source test automation framework built by Microsoft, released in 2020. It allows you to write automated tests for web applications across Chromium, Firefox, and WebKit — using a single, unified API.

But here's what makes Playwright different from tools you may have used before: it doesn't control browsers from the outside. It communicates directly with the browser at the protocol level — which means it's faster, more reliable, and aware of things happening inside the page in real time.

"Playwright doesn't knock on the browser's door and wait. It's already inside the room."

As a QA engineer, you don't need to understand every internal detail — but knowing why Playwright behaves the way it does will help you write better tests, debug failures faster, and explain your architecture choices confidently.

// 02 — Architecture

Playwright's Architecture — Layer by Layer

Playwright is built in a layered architecture. Each layer has a specific responsibility, and they communicate with each other in a well-defined way.

Playwright Architecture Stack
Your Test Code

↕ calls
Playwright Node.js / Python / Java API
page.goto() · page.click() · expect(locator).toBeVisible()
↕ WebSocket (JSON messages)
Browser Server Process
CDP (Chromium) · Firefox Protocol · WebKit Protocol
↕ spawns & controls
Browser Engines
Bundled browser binaries — not your installed browser
🟠 Chromium
🦊 Firefox
🧭 WebKit (Safari)

Layer 1: Your Test Code

This is what you write — test files using Playwright's API. You write human-readable test steps. Playwright translates those into browser instructions behind the scenes.

Layer 2: The Playwright API

Available in TypeScript/JavaScript, Python, Java, and .NET. This API is your contract with Playwright. Methods like page.click(), page.fill(), and locator.waitFor() are defined here.

Layer 3: Browser Server / Protocol Bridge

This is Playwright's secret weapon. It uses a persistent WebSocket connection to send JSON commands directly to the browser's internal debugging protocol — CDP for Chromium, custom protocols for Firefox and WebKit. This connection stays open for the entire test session, making it fast and stateful.

Layer 4: Bundled Browser Binaries

Playwright ships with its own browser binaries, separate from whatever Chrome or Firefox you have installed. This ensures version consistency — no "it works on my machine" failures due to browser version mismatches.

// 03 — Execution Flow

How a Playwright Test Executes — Step by Step

Let's trace what happens when you run a single test:

01

Test Runner Starts

You run npx playwright test. The Playwright Test runner discovers your test files, sets up workers, and begins execution. Each worker is an isolated Node.js process.

02

Browser Launch

Playwright spawns a browser process from its bundled binaries. The browser starts in headed or headless mode based on your config. A WebSocket server opens inside the browser.

03

Browser Context Created

A Browser Context is created — think of it as a fresh, isolated browser profile. It has its own cookies, localStorage, and session state. This is how Playwright achieves true test isolation without restarting the browser.

04

Page Object Created

A new page (browser tab) is opened inside the context. This is the page object in your test. All your interactions happen through this object.

05

Commands Sent via WebSocket

When you call page.goto('https://example.com'), Playwright sends a JSON message over the WebSocket to the browser's protocol. The browser acts on it and sends back a confirmation with any result data.

06

Auto-Waiting Kicks In

Before every action, Playwright checks that the element is: visible, stable (not animating), enabled, and editable (for inputs). This is called actionability checking — and it eliminates most flakiness automatically.

07

Assertions Evaluate

Playwright's web-first assertions (via expect()) automatically retry until the expected condition is true or the timeout is reached. No manual waitForSelector needed.

08

Cleanup and Teardown

After the test, the context is closed (clearing all state), and the browser process is either reused for the next test or shut down. Artifacts like screenshots, videos, and traces are saved if configured.

// 04 — Real Code

Playwright in Action — QA-Focused Examples

Example 1: Basic Login Test

login.spec.ts
import { test, expect } from '@playwright/test'; test('user can log in successfully', async ({ page }) => { // Step 1: Navigate to the login page await page.goto('https://myapp.com/login'); // Step 2: Fill form fields — Playwright waits for elements automatically await page.fill('[data-testid="email"]', 'qa@example.com'); await page.fill('[data-testid="password"]', 'securePass123'); // Step 3: Click the button await page.click('button[type="submit"]'); // Step 4: Assert the dashboard is visible — retries automatically await expect(page.locator('h1')).toHaveText('Welcome back!'); });

Example 2: Isolated Contexts for Parallel Tests

parallel-contexts.spec.ts
// Two users logged in simultaneously — no cookie conflicts! test('admin and regular user can work simultaneously', async ({ browser }) => { // Each context = isolated browser session const adminContext = await browser.newContext({ storageState: './auth/admin.json' }); const userContext = await browser.newContext({ storageState: './auth/user.json' }); const adminPage = await adminContext.newPage(); const userPage = await userContext.newPage(); await adminPage.goto('/admin/dashboard'); await userPage.goto('/dashboard'); // Clean up await adminContext.close(); await userContext.close(); });

Example 3: API + UI Combined Test

api-ui.spec.ts
// Use Playwright's request context to call APIs AND test the UI test('order created via API shows in UI', async ({ page, request }) => { // Create order via API (faster than UI flow) const response = await request.post('/api/orders', { data: { productId: 'ABC123', qty: 2 } }); const { orderId } = await response.json(); // Verify the UI shows this order await page.goto(`/orders/${orderId}`); await expect(page.locator('.order-status')).toContainText('Confirmed'); });
// 05 — Pros & Cons

Playwright: Honest Pros and Cons

✅ Strengths
  • ⚡Auto-waiting built in — no more Thread.sleep() or flaky explicit waits. Playwright waits for actionability before every interaction.
  • 🌐True cross-browser — Chromium, Firefox, and WebKit from one API and one codebase.
  • 🔒Isolated browser contexts — parallel tests don't share cookies or state. Real isolation, not workarounds.
  • 📸Rich debugging tools — Trace Viewer, screenshot-on-failure, video recording, and --ui mode out of the box.
  • 🔗API testing built in — request fixture lets you test REST APIs alongside UI in the same test.
  • 🛡️Network interception — mock APIs, block ads, simulate slow networks without extra tools.
  • 🚀Fast by default — WebSocket protocol is far faster than HTTP-round-trip tools like Selenium WebDriver.
  • 🎭Multi-language support — TypeScript, Python, Java, .NET. Use what your team already knows.
⚠️ Limitations
  • 📈Learning curve — concepts like Browser, Context, and Page hierarchy can be confusing at first for manual QA engineers.
  • 🔮Relatively newer ecosystem — fewer Stack Overflow answers and community plugins compared to Selenium's decade-long head start.
  • 🌐No IE support — if your project needs Internet Explorer, Playwright cannot help you (but arguably neither should you).
  • ⚙️Node.js dependency (JS/TS) — requires Node.js setup and npm understanding for JavaScript users, which some QA teams find intimidating.
  • 💾Bundled browser size — Playwright downloads its own browser binaries (~200MB+), which can slow CI/CD pipeline setup time initially.
  • 📱Mobile testing is emulation — Playwright emulates mobile viewports but cannot test real native iOS or Android apps.
// 06 — Comparison

Playwright vs Selenium — A Practical Comparison

Both are excellent tools with different philosophies. Here's an honest, side-by-side breakdown of what matters for QA engineers:

Feature ⚡ Playwright 🔸 Selenium
Protocol WebSocket (CDP / custom) — persistent connection HTTP WebDriver protocol — request per command
Speed Faster — direct protocol, no HTTP overhead Slower — each command is an HTTP round-trip
Auto-waiting Built-in — actionability checks before every action Manual — you write explicit waits or use FluentWait
Browser Support Chromium, Firefox, WebKit (Safari engine) Chrome, Firefox, Edge, Safari, IE (via drivers)
Test Isolation Browser Contexts — isolated per test, no restart needed Manual — restart driver or manage cookies manually
Parallel Execution Native — built into the test runner Needs Selenium Grid or TestNG configuration
API Testing Built-in — request fixture included Not included — need RestAssured or separate library
Debugging Tools Trace Viewer, Playwright Inspector, UI Mode, Video Screenshots via listeners; third-party reporting
Network Interception Native — page.route() built in Not native — needs BrowserMob Proxy or WireMock
Community & Ecosystem Growing fast — strong Microsoft backing Mature — 15+ years, huge community and resources
Language Support JS/TS, Python, Java, .NET JS, Python, Java, C#, Ruby, Kotlin
Mobile Testing Emulation only (viewport simulation) Real device testing via Appium integration
Cloud Execution BrowserStack, LambdaTest, Sauce Labs Selenium Grid, all major cloud providers
When to Choose Modern web apps, CI/CD-first teams, new projects Legacy projects, mobile needs, large existing codebase

"Selenium taught us how to automate. Playwright showed us how to automate without fighting the browser."

// 07 — Summary

Key Takeaways for QA Engineers

🏗️

Architecture matters

WebSocket + protocol-level communication is why Playwright is fast and reliable — not magic.

🔒

Context = Isolation

Browser contexts give you fresh sessions per test without restarting the browser. Use them for parallel tests.

⏳

Stop writing explicit waits

Playwright's auto-waiting handles 90% of timing issues. Let the framework do the work.

🔗

UI + API in one test

Use the built-in request fixture to set up data via API, then verify via UI.

🎭

Trace Viewer is your best friend

When tests fail in CI, use traces to replay exactly what happened — screenshot by screenshot.

🚀

It's not replacing Selenium yet

For new projects and modern apps, Playwright is the clear choice. For large Selenium codebases, migrate gradually.
